# Dabba Match — notes for Claude Code

## What this is
A no-login web app: users set up a profile (body stats, goal, diet), pick ingredients they have, and get 3 AI-suggested dishes sized to one meal's macro target. A Today tab tracks what they've eaten against the day's target. Owner is a beginner returning to coding; explain changes in plain language and keep the setup simple.

## Structure
- `public/index.html` — the entire frontend: HTML, CSS and vanilla JS in one file. No framework, no build step. Deployed as static files.
- `api/dishes.js` — Vercel Function (Web `Request`/`Response`, named `GET`/`POST` exports). Validates input, builds the prompt server-side, calls the AI provider, streams plain text back: exactly 3 lines, one minified JSON dish per line (2 lines when the payload has `mode: "gap"`). Walks a model fallback chain (`GEMINI_MODELS`): on 404/429/500/503, or no text within 7 s (`FIRST_TEXT_MS`), it tries the next model; a 10 s stall mid-answer (`STALL_MS`) counts as stopping partway; if one stops partway it asks the next only for the missing dishes (finished names passed as "already shown"). The server parses lines itself so it knows which dishes are finished. Waits for the first dish before replying, so total failure returns a real 503/429 JSON error. Lines with a comma where a field's colon belongs (`"tagline","..."`, a gemini-3.5-flash-lite habit) are repaired by `fixFieldCommas()` before parsing. Dishes whose protein, carbs and fat all equal the target (copied, not calculated) are always dropped and topped up from the next model, never shown. So are dishes with no ingredient list or steps, and dishes whose honest time (see `lib/dish.js`) breaks the time filter; if every model has been tried and dishes are still missing, the fastest of those too-slow dishes are sent with `overTime: true` (shown as "Over your time limit") instead of an error, then the closest off-target ones (with honest times, also flagged `overTime` if they break the filter). Times are made honest before the macro check, so every dish that reaches the page has honest times. No new model is started after `CHAIN_BUDGET_MS` (40 s) because Vercel stops the function at 60 s. A `[dishes] too-slow ...` warning logs claimed vs honest times. Logs one `[dishes] ... answered_by=...` line per request, plus a `[dishes] unreadable model=...` warning with a sample of any reply text that couldn't be read as a dish, and a `[dishes] cut-off model=... finish=...` warning when a reply stops mid-dish. The chain shows each model's finish reason in braces, e.g. `{STOP}`, `{MAX_TOKENS}`, `{no finish}`. Gemini sometimes reports "high demand" as plain JSON after the events; `sseText()` treats that as a 503.
- `lib/prompt.js` — `validatePayload()` and `buildPrompt()`. The client never sends raw prompts; keep it that way so the endpoint can't be abused as a general chatbot. The payload carries `ref` (per-100 g macros of picked staples, numbers only, only for names in the kitchen), `time` (`any`/`quick` ≤20/`medium` ≤40/`long` 40–90; old `15/30/45` still accepted) and `prepped` (protein already cooked: only reheating counts).
- Dish line schema: `{name, tagline, prepMin, cookMin, soakHours, protein, carbs, fat, uses[], extra[], ingredients:[{name, qty, unit, g?}], steps[]}`. Quantities are for ONE serving; macros are per serving. Kitchen units only (tsp, tbsp, cup, glass, katori, pinch, pieces, inch, cloves, "to taste"); grams plus a household measure for weighed items. Steps are one action each and refer to ingredients as `{n}` (1-based), never with amounts, so they stay right when scaled.
- `lib/ai.js` — shared one-shot AI helper (`askJson` walks the same model chain, accepts an optional photo, returns one JSON object; gives up after `totalMs` 50 s) used by the endpoints below.
- `api/recipe.js` — POST `{dish,diet,avoid}` → one dish (same schema as `/api/dishes`, 1 serving) for "Know what you want to cook?". Macros recomputed from the ingredients. Replies that share no word with what was typed (gibberish turned into some other recipe) are refused with 422 (`relatedName()`, allows small typos and common Hindi/English pairs like anda/egg).
- `api/scan.js` — POST `{image}` (data URL, shrunk in the browser) → ingredients seen in a photo; names matched to the app's own list via `lookup()`.
- `api/food.js` — POST `{text?,image?}` → `{title,items[],total,note}` for the Today food log. kcal always equals protein×4 + carbs×4 + fat×9, like everywhere else in the app. Estimates are only a starting point: the page makes the user review/edit before logging.
- `lib/nutrition.js` — per-100 g table + `recompute(dish)`: macros recalculated server-side from the ingredient list; `/api/dishes` never trusts the model's own macros. When a dish is more than ~8% off, `fitToTarget()` nudges ingredient amounts within bounds (oil/cream 0.3–1.3×, main items 0.4–1.8×, veg 0.7–1.5×, spices fixed), rounds them to kitchen numbers and keeps the change only if it is closer; dishes still more than ~15% off are dropped and topped up from the next model. Keep TABLE in step with `STAPLES` in index.html when ingredients are added. `PATTERNS` maps recipe names to rows (most specific first); `gramsOf()` turns kitchen units into grams (`CUP_G`, `KATORI_G`, `PIECE_G` for light/heavy items; a roti is ~30 g atta). Skipped when `AI_PROVIDER=mock`.
- `lib/dish.js` — `checkTimes()` raises prep/cook/soak to honest minimums from what the dish uses (soaked rajma/chole 45 min + 6 h soak, mutton 60, chicken 25 / curry 40, chaap 25 / masala 40, toor/chana dal 35, moong/masoor 25, raw rice 25, marinade 35, rotis from atta +15, anything heated 15, about 2 min chopping per vegetable). `fitsTime()` applies the filter (soak-ahead dishes only fit `long`).
- `dev-server.mjs` — zero-dependency local server that mimics Vercel. Loads `.env.local`.
- `vercel.json` — serves `public/` as the site; 60s max duration for the function.

## Commands
- `npm run dev` — local server at http://localhost:3000 using the real provider from `.env.local`.
- After changing `api/` files, restart the dev server (Ctrl+C, `npm run dev`); the browser page reloads on its own, the server does not.
- `npm run dev:mock` — same, with fake dishes (no API key, no cost). Prefer this while developing UI.
- Deploy: push to `main` on GitHub (repo `pkhillan04/dabba-match`); Vercel builds it automatically. `npx vercel --prod` still works for a manual deploy.

## Key frontend concepts (public/index.html)
- `state` object persisted to localStorage key `dabbamatch_v4` (`save()` / `load()`). `load()` migrates the older `dabbamatch_profile_v3` format. If you change the state shape, keep old data loading.
- `calcTargets()` — macro engine: Mifflin-St Jeor BMR × activity factor; goal adjustment from % bodyweight per week (7,700 kcal/kg), capped at −25% of TDEE for cuts; bulks are a % of TDEE (Gentle +5%, Steady +7.5%, Faster +10%); activity labels are honest (Desk job + workouts = 1.375); protein g/kg by goal (lose 2.2, recomp 2.0, maintain 1.8, gain 2.0) on a reference weight capped at BMI 27.5; fat 25% kcal with 0.7 g/kg floor; carbs remainder; training days ~5% above rest days with the weekly average preserved; floors 1,200 kcal (female) / 1,500 (male). If you change this, re-test against known profiles.
- `mealTarget()` — daily target ÷ meals per day, skewed by macro focus.
- `STAPLES` — `[name, dietTag, kcal, protein, carbs, fat, basis, source]` per 100 g. Basis is `dry` (dals, rice, beans, soya chunks, flours: uncooked), `raw` (meat, fish, eggs, veg) or `sold` (as packed); recipes weigh the same way. Source `U<id>` = USDA FoodData Central SR Legacy record, `L` = Indian pack label, `I` = IFCT 2017 as quoted in summaries. `RENAMED` maps old kitchen names to new ones; `migrateState()` (called from `load()`) applies it and maps old time values.
- Recipe view (`recipeHTML()`): servings stepper (default 2 on Cook, 1 on Close my gap; `servingsFor`, in memory), macros per serving and total, ingredient checklist (`checkedIng`), numbered steps. `normIng()` turns ml/kg/veg-grams into kitchen units; `scaleIng()` scales on the client (spices ×servings^0.75, oil ×servings^0.8, rounded to pinch / 1/4 tsp / 1/2 tbsp; eggs and slices whole; lemons and onions in halves; grams to 5 g); `fmtFrac()` prints 1/2, 1 1/4. "Cooked this" logs one serving.
- `streamDishes()` — shared fetch + stream parser for `/api/dishes` (uses `tryParseLine()`, calls back per dish). `generate()` (Cook tab) and `closeGap()` (Today tab) both use it.
- Sheets/popups (`openSheet`/`closeSheet`): photo scan checklist, recipe-by-name, food-log review, and Cook mode (`startCook`: one step per screen, animated SVG scene chosen by `sceneKind()`, timers parsed from "N minutes", screen wake lock, arrow keys/swipe). New state fields: `style` (goal style chip, validated per goal by `renderStyle`), `foodHistory`, `dismissed` (input warnings).
- Input warnings in the calculator (`inputWarnings`) are dismissible, with a one-tap "convert from lb".
- Two screens: Cook (`#mainView`) and Today (`#todayView`), switched by `state.view` via `renderView()`.
- Today tab: `state.usualMeals` (set once, ticked daily) and `state.dayLog` (`{ "YYYY-MM-DD": [items] }`, last 14 days, pruned in `saveLog()`). "Cooked this" (`markCooked(name, dish)`) also logs the dish. `gapTarget()` = what's left today, capped at ~1 meal; "Close my gap" sends it with `mode:"gap"`.
- Tone on Today is no-shame: going over target shows "Target reached", never red or warning colours.
- Rendering is plain functions (`renderTarget`, `renderKitchen`, `renderResults`, `renderProfile`, …) writing innerHTML. Always pass user or AI text through `esc()`.
- Design tokens are CSS variables on `:root` with dark-mode overrides. Use the tokens; don't hardcode colors. Fonts: Bricolage Grotesque (display) and Figtree (body).

## Rules
- Never put API keys in `public/` or commit `.env.local`.
- Keep the app working without login.
- Test changes with `npm run dev:mock` in a browser at phone width (~390px) and desktop before deploying.
